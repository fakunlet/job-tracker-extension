# Job Application Tracker

A Chrome extension and a Spring Boot REST API for keeping track of jobs you've
applied to.

Click the extension icon, paste the company, role, and job posting URL into the
popup, and hit Save. The application is stored in PostgreSQL. If you try to save
the same URL twice, the API rejects it and the popup tells you you've already
applied to that job.

Every response in this README was captured from a real run against a live
database — none of it is written by hand.

## Tech stack

| Part | Technology |
| --- | --- |
| Backend | Java 17, Spring Boot 3.4.1, Spring Web, Spring Data JPA, Bean Validation |
| Database | PostgreSQL 16 (in Docker) |
| Build | Maven |
| Extension | Chrome Manifest V3, plain HTML/CSS/JavaScript — no frameworks |

## Running the backend

### 1. Start the database

From the project root:

```bash
docker compose up -d
docker compose ps
```

Wait until `STATUS` reads `Up (healthy)` and `PORTS` shows
`0.0.0.0:5332->5432/tcp`.

Port 5332 is used on the host instead of the usual 5432 so this doesn't clash
with any PostgreSQL already installed on your machine.

| Setting | Value |
| --- | --- |
| Database | `jobtracker` |
| User | `apiuser` |
| Password | `apipass` |
| Host port | `5332` |

### 2. Start the API

```bash
cd backend
mvn spring-boot:run
```

You're looking for these lines:

```
HikariPool-1 - Added connection org.postgresql.jdbc.PgConnection@...
Tomcat started on port 8080 (http) with context path '/'
Started JobTrackerApplication in 5.908 seconds
```

The first line is the real proof the database connection worked. On the very
first run Hibernate also creates the table, because
`spring.jpa.hibernate.ddl-auto=update`:

```sql
create table job_application (
    id bigint generated by default as identity,
    applied_date date not null,
    company varchar(255) not null,
    role varchar(255) not null,
    status varchar(20) not null check (status in ('APPLIED','INTERVIEWING','OFFER','REJECTED')),
    url varchar(255) not null,
    primary key (id)
)
```

The API is then at `http://localhost:8080/api/v1/applications`.

## Loading the extension

1. Open `chrome://extensions` in Chrome.
2. Turn on **Developer mode** (top-right toggle).
3. Click **Load unpacked** and select the `extension/` folder.
4. The extension appears in your toolbar. Pin it if you want it always visible.

**After changing any file in `extension/`, go back to `chrome://extensions` and
click the reload icon on the extension card.** Chrome does not pick up changes
automatically, and this is the single most common reason an edit "does nothing."

The manifest asks for one thing only:

| Entry | Why it's needed |
| --- | --- |
| `host_permissions: ["http://localhost:8080/*"]` | Without it Chrome blocks the popup's `fetch` to the API. |

There are no `permissions` at all. Because the popup is a plain form that you
type into, the extension never reads the page you're on, so it doesn't need
`activeTab` or `scripting`. Asking only for what's actually used is good
practice — every extra permission is one more thing a user has to trust.

## Endpoints

Base path: `/api/v1/applications`

| Method | Path | Body | Success | Errors |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/applications` | `{company, role, url}` | `201 Created` + saved record | `400` blank field, `409` duplicate URL |
| GET | `/api/v1/applications` | — | `200 OK` + list, newest first | — |

`status` defaults to `APPLIED` and `appliedDate` defaults to today, so neither
needs to be sent.

Errors always come back in the same shape, `{status, message}`, so the extension
can read `message` without caring which kind of failure it was.

## Example requests

These are for **bash** (macOS, Linux, WSL, or Git Bash on Windows). For Windows
PowerShell see the note at the end.

### Create an application

```bash
curl -s -X POST http://localhost:8080/api/v1/applications \
  -H "Content-Type: application/json" \
  -d '{"company":"Shopify","role":"Backend Developer Intern","url":"https://jobs.shopify.com/postings/12345"}'
```

```json
{"id":1,"company":"Shopify","role":"Backend Developer Intern","url":"https://jobs.shopify.com/postings/12345","status":"APPLIED","appliedDate":"2026-09-27"}
```

`201 Created`. Note `status` and `appliedDate` were filled in by the server.

### Create a second one

```bash
curl -s -X POST http://localhost:8080/api/v1/applications \
  -H "Content-Type: application/json" \
  -d '{"company":"Wealthsimple","role":"Junior Software Engineer","url":"https://www.wealthsimple.com/careers/jr-swe-2026"}'
```

```json
{"id":2,"company":"Wealthsimple","role":"Junior Software Engineer","url":"https://www.wealthsimple.com/careers/jr-swe-2026","status":"APPLIED","appliedDate":"2026-09-27"}
```

### List all applications (newest first)

```bash
curl -s http://localhost:8080/api/v1/applications
```

```json
[{"id":2,"company":"Wealthsimple","role":"Junior Software Engineer","url":"https://www.wealthsimple.com/careers/jr-swe-2026","status":"APPLIED","appliedDate":"2026-09-27"},{"id":1,"company":"Shopify","role":"Backend Developer Intern","url":"https://jobs.shopify.com/postings/12345","status":"APPLIED","appliedDate":"2026-09-27"}]
```

`id` 2 comes before `id` 1 — newest first.

### Duplicate URL is rejected

Posting the first application's URL a second time:

```bash
curl -s -X POST http://localhost:8080/api/v1/applications \
  -H "Content-Type: application/json" \
  -d '{"company":"Shopify","role":"Backend Developer Intern","url":"https://jobs.shopify.com/postings/12345"}'
```

```json
{"status":409,"message":"Already applied to this job"}
```

`409 Conflict`. This exact `message` is what the popup displays.

### Blank fields are rejected

```bash
curl -s -X POST http://localhost:8080/api/v1/applications \
  -H "Content-Type: application/json" \
  -d '{"company":"","role":"","url":""}'
```

```json
{"status":400,"message":"url must not be blank, role must not be blank, company must not be blank"}
```

`400 Bad Request`, listing every field that failed so all of them can be fixed
at once.

### The request the extension actually makes

The popup runs on a `chrome-extension://` origin, which is different from
`http://localhost:8080`, so the browser needs the server's permission to read
the response. Simulating that with an `Origin` header:

```bash
curl -i -X POST http://localhost:8080/api/v1/applications \
  -H "Origin: chrome-extension://abcdefghijklmnop" \
  -H "Content-Type: application/json" \
  -d '{"company":"Shopify","role":"Careers at Shopify","url":"https://www.shopify.com/careers"}'
```

```
HTTP/1.1 201
Access-Control-Allow-Origin: chrome-extension://abcdefghijklmnop
```

That `Access-Control-Allow-Origin` header is what `CorsConfig` adds. Without it
the popup's `fetch` would fail with a CORS error even though the record saved
fine — and it's returned on error responses too, which is what lets the popup
display the 409 message rather than a generic failure.

### Windows PowerShell note

In PowerShell, bare `curl` is an alias for `Invoke-WebRequest` and takes
different flags, so use `curl.exe`. Inline JSON also doesn't survive
PowerShell's argument parsing — it arrives mangled and the API answers
`400 Bad Request`. Put the body in a file instead:

```powershell
'{"company":"Shopify","role":"Backend Developer Intern","url":"https://jobs.shopify.com/postings/12345"}' |
  Set-Content -Encoding ascii app.json

curl.exe -s -X POST http://localhost:8080/api/v1/applications `
  -H "Content-Type: application/json" -d "@app.json"
```

Or use PowerShell's own client:

```powershell
$body = '{"company":"Shopify","role":"Backend Developer Intern","url":"https://jobs.shopify.com/postings/12345"}'
Invoke-RestMethod -Uri http://localhost:8080/api/v1/applications `
  -Method Post -ContentType "application/json" -Body $body
```

GET needs no body and works inline: `curl.exe -s http://localhost:8080/api/v1/applications`

## Limitations and future work

Known and deliberate, given the scope:

- **Details are typed in by hand.** The popup doesn't read the job posting, so
  you copy and paste the company, role, and URL. Reading the page automatically
  would mean scraping, and every job site is laid out differently, so it would
  be guesswork that's wrong often enough to need correcting anyway.
- **No authentication.** Anyone who can reach the API can read and write every
  application. There are no user accounts, so the data isn't tied to a person.
  Spring Security with a login would be the fix.
- **Local only.** The API runs on `localhost:8080` and the database in a local
  Docker container. Nothing is deployed, so applications saved on one machine
  aren't available on another.
- **No way to view or edit saved applications in the extension.** `GET` exists on
  the API but the popup only writes. A list view with the ability to change
  `status` from `APPLIED` to `INTERVIEWING` is the obvious next feature.
- **`ddl-auto=update` manages the schema.** Fine here, but a real project should
  use versioned migrations (Flyway or Liquibase) so schema changes are reviewable
  and repeatable.
- **Duplicate detection is exact-match on URL.** The same job posted at two
  slightly different URLs, or with a `?ref=` tracking parameter added, counts as
  two different jobs.
- **No automated tests.** Everything here was verified by hand with curl.
